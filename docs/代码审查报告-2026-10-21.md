## 一、总体结论

**综合评分：48 / 100（不及格，原型阶段可用，离可上线有明确差距）**

这是一套**功能完成度相当高、工程组织清晰、但安全模型整体缺失**的原型。业务链路（下单→支付→状态机→骑手结算）能跑通，金额计算用整数分、服务端重算、状态机集中校验、并发抢单用条件更新——这些是有意识做对的工程决策，水平不低。

但它的安全模型是"演示级"的：**身份靠请求头直传、支付回调无验签、App 允许明文 HTTP、未认证请求自动获得超管权限**。这四项任意一项都足以让整套业务被零成本攻破。代码里大量注释写着"真实实现应替换为 JWT"，说明作者清楚这些是临时方案——问题是**它们被当作可用实现交付了**。

## 二、P0 致命问题（可被直接利用，必须优先修复）

### S1. 支付回调无验签 —— 可零成本"白嫖"订单

| 项 | 内容 |
|---|---|
| 位置 | `backend/.../controller/PayController.java:45-49`<br>`backend/.../service/PayService.java:122-145`<br>`frontend/src/api/index.js:35` |
| 风险 | 🔴 致命 |

`POST /api/v1/pay/notify/{payNo}` 是一个公开接口，`PayService.notify()` **不校验签名、不校验来源 IP、不校验调用方身份**，直接 `settle()` 把支付单置为 `SUCCESS` 并推进订单到"待接单"。

更严重的是 `frontend/src/api/index.js:35` 导出了 `notifyPay()`，前端支付页在"模拟支付"时主动调用它。也就是说：**支付成功与否由客户端说了算。**

攻击路径：
```
1. 正常下单，拿到 orderNo → 调 /pay/prepay 拿到 payNo
2. 不付款，直接 POST /api/v1/pay/notify/{payNo}
3. 订单变"已支付"，商家开始出餐，平台账上没钱
```

**修复建议**
1. 回调接口只接受渠道服务器调用，必须验签：支付宝用 RSA2 验签 + `app_id` 校验，微信 V3 用平台证书验签 + 解密。
2. 回调报文中的金额必须与 `payment.amount` 比对，不一致直接拒绝并告警。
3. 前端**禁止**调用回调接口；`notifyPay()` 从 `api/index.js` 移除。
4. 生产环境强制关闭 `xingguang.mock-pay-enabled`（当前 `application.yml:51` 为 `true`）。

### S2. 鉴权是"信任请求头"，任意人可冒充任意身份

| 项 | 内容 |
|---|---|
| 位置 | `support/CurrentUser.java:20-38`<br>`support/CurrentAdmin.java:20-55`<br>`support/CurrentRider.java`<br>`frontend/src/api/http.js:22, 30` |
| 风险 | 🔴 致命 |

三端身份全部靠请求头明文传递，且传的就是**数据库主键**：

| 端 | 请求头 | 实际值 |
|---|---|---|
| 用户端 | `X-User-Id` | `app_user.id` |
| 骑手端 | `X-Rider-Id` | `rider.id` |
| 管理端 | `X-Admin-Token` | `admin_user.id` |

前端还把它写死在 axios 默认头里（`http.js:22` 的 `'X-User-Id': '1'`）。这意味着：

- 改一个 header 就能读别人的订单、地址、支付单
- `X-Admin-Token: 1` 直接成为超级管理员
- 无任何过期、无签名、无受众隔离，token 可枚举（1,2,3...）

**修复建议**
1. 引入 JWT（HS256/RSA256），payload 含 `sub`/`role`/`aud`/`exp`，`aud` 区分 `USER`/`RIDER`/`ADMIN`。
2. 三类 token 互不通用——用户 token 不能调骑手接口，骑手 token 不能调管理接口。
3. 用 `HandlerInterceptor` 或 Spring Security Filter 做统一入口校验（当前全项目 **0 个 Filter/Interceptor**，见 M3）。
4. 前端删除默认身份头，改为登录后写入 `Authorization: Bearer <token>`。

### S4. `/admin/orders/{orderNo}/advance` 缺权限校验

### S5. App 全链路允许明文 HTTP

| 项 | 内容 |
|---|---|
| 位置 | `frontend/capacitor.config.json` |
| 风险 | 🔴 致命 |

```json
"server": { "androidScheme": "http", "cleartext": true },
"android": { "allowMixedContent": true }
```

三个开关同时打开，意味着 App 内所有请求可以走明文 HTTP，且允许 HTTPS 页面加载 HTTP 资源。用户手机号、收货地址、订单金额、支付凭据全部可被同一 WiFi 下的中间人嗅探和篡改。

这与"数据加密传输"的要求直接冲突。

**修复建议**
1. `androidScheme` 改 `https`，`cleartext` 改 `false`，`allowMixedContent` 改 `false`。
2. 增加 `android/app/src/main/res/xml/network_security_config.xml`，显式声明仅允许 HTTPS。
3. 生产环境后端强制 HTTPS（nginx 已配 443，但缺少 HSTS）。

## 三、P1 高危问题

### H1. 已支付订单取消无退款 —— 资金黑洞

| 项 | 内容 |
|---|---|
| 位置 | `service/OrderService.java:303-315`<br>`service/AdminService.java:224-243` |
| 风险 | 🟠 高 |

`cancel()` 只把订单状态改成 `CANCELED`，**完全没有触碰 `payment` 表**。全仓搜索无任何 `refund` 实现。

而 `OrderStateMachine` 允许 `PREPARING → CANCELED`（29 行），`actionsOf` 也给 `PREPARING` 状态返回了 `CANCEL` 按钮（`OrderStateMachine.java:144-150`）。也就是说：

> 用户付了钱 → 商家已接单备餐 → 用户点取消 → 订单显示"已取消" → **钱不退，支付单仍是 SUCCESS**

管理端 `adminCancel()` 同理，且更宽松（除终态外都能取消）。

**修复建议**
1. 新增 `RefundService`，按渠道实现退款（余额即时退、支付宝/微信走原路退回）。
2. `cancel()` 中判断 `payment.status == SUCCESS` 则触发退款，并新增 `refund` 记录表。
3. 状态机区分 `CANCELED`（未支付取消）与 `REFUNDED`（已支付退款）——目前两个状态都存在，但代码没用对。

### H2. `adminCancel` 绕过状态机

`AdminService.java:232-239` 直接 `order.setStatus(CANCELED)`，未走 `OrderStateMachine.require()`。状态机中 `DELIVERING` 不允许转 `CANCELED`（31 行），但管理端可以从"配送中"直接取消，破坏一致性。

**修复建议**：统一走 `orderService.transferStatus(order, OrderStatus.CANCELED, "ADMIN", reason)`。

### H3. CORS 通配 + 允许凭据

`config/WebConfig.java:15-21`：

```java
.allowedOriginPatterns("*")
.allowCredentials(true)
```

任意站点可携带用户凭据跨域调用全部接口。**修复建议**：白名单化（`https://app.xingguang.example.com`、`http://localhost:5173`），生产禁用 `*`。

### H4. 明文数据库凭据 + 关闭 SSL

`application.yml:11-13`：`password: "123456"`、`useSSL=false`、`allowPublicKeyRetrieval=true`。

凭据进版本库 + 传输明文。**修复建议**：`${XG_DB_PASSWORD:}` 环境变量注入；生产 `useSSL=true`；`123456` 立即轮换。

### H5. 上传仅校验 Content-Type，可伪造 → 存储型 XSS

`ObjectStorageService.java:98-101` 只比对 `file.getContentType()`，这是**客户端可控**的。攻击者把 HTML/SVG 改名为 `.png` 并伪造 `Content-Type: image/png` 即可上传。

叠加 `scripts/minio-init.ps1` 中"桶设置匿名只读、直链预览"的设计（脚本注释明确写了这一点），上传的文件可通过 `public-base-url` 直接访问 → **存储型 XSS**。

**修复建议**
1. 校验文件头魔数（`FF D8 FF` / `89 50 4E 47` / `RIFF....WEBP`），而非信任 Content-Type。
2. 图片重新编码（`ImageIO.read` → 重新写出），剥离任何嵌入脚本。
3. 响应加 `X-Content-Type-Options: nosniff`、`Content-Disposition: inline`。
4. 商家资质等私密素材用私有桶 + 签名 URL，不进公开桶。

### H6. 管理端密码 MD5 无盐

`AdminService.java:449, 457-469`。MD5 无盐可被彩虹表秒破，`123456` 的 MD5 是公开常数。

**修复建议**：BCrypt（`spring-security-crypto`），或至少 PBKDF2 + 每用户独立盐。

### H7. `overview()` 全表扫描 —— 后台首页必炸

`AdminService.java:71`：

```java
List<Orders> all = ordersMapper.selectList(Wrappers.<Orders>lambdaQuery());  // 无条件，全表
```

把**所有订单**读进内存，然后用 stream 算 12 个指标（今日订单、GMV、状态分布……）。订单量到万级就会超时，到十万级直接 OOM。

**修复建议**：改用 SQL 聚合（`SELECT status, COUNT(*), SUM(pay_amount) FROM orders GROUP BY status`），今日数据加 `WHERE created_at >= ?`。新增 `OrdersMapper` 自定义查询或 XML。

### H8. 异常信息直接回传前端

`GlobalExceptionHandler.java:41`：`"系统繁忙，请稍后重试：" + e.getMessage()`。

SQL 异常会把表名、字段名、SQL 片段返回给调用方。**修复建议**：对外只返回 `traceId` + 通用文案，详细信息仅写日志。

### H9. `ratingMonitor()` SQL 条件错配

`AdminService.java:307-308`：

```java
complaintMapper.selectCount(Wrappers.<Complaint>lambdaQuery()
        .eq(Complaint::getOrderNo, "").or().like(Complaint::getContent, s.getName()));
```

`.or()` 未加括号包裹，实际生成 `(order_no = '' OR content LIKE '%店名%')`，前面若有其他条件会被 OR 短路。当前虽然只有这一个条件，但"用内容模糊匹配店名"本身就是错误口径——**客诉数统计完全不可信**。

**修复建议**：`Complaint` 表加 `shop_id` 字段，按 `shop_id` 统计。

## 八、整体改进建议

### 8.1 值得肯定的设计

避免只讲问题，以下几处是**有意识做对**的，改造时应保留：

1. **金额用整数分 + 服务端唯一计算源**（`AmountCalculator`）——杜绝浮点误差，前端改价无效。这是支付类系统的正确做法。
2. **状态机集中定义**（`OrderStateMachine`）——两类订单共用一套状态，自取单用替换而非新增状态，设计干净。
3. **并发抢单用条件更新**（`RiderService.grab()` 的 `UPDATE ... WHERE rider_id IS NULL`）——不靠锁，靠影响行数，正确。
4. **关键表都有唯一索引**（`uk_order_no`、`uk_pay_no`、`uk_key_scene`、`uk_phone`、`uk_username`）——数据库层兜底意识在。
5. **手机号脱敏贯穿 VO 层**（`Mask.phone`）——不是临时补的。
6. **e2e 覆盖 118 个断言、10 个业务分组**——原型阶段能做到这个覆盖度很少见。

### 8.2 核心判断

这个项目的**问题不是"不会写"，而是"知道该怎么做但按演示标准交付了"**。代码里那些"真实实现应替换为 JWT""生产环境必须为 false"的注释，说明作者完全清楚差距在哪。

所以整改的关键不是补知识点，而是**建立一道闸门**：把"演示可用"和"生产可用"的边界显式化。建议：

1. **配置分层**：`application-dev.yml` / `application-prod.yml`，所有 mock 开关只在 dev 存在；prod 启动时校验 `mock-pay-enabled == false`，否则拒绝启动。
2. **接口分层**：`/api/v1/**`（正式）与 `/api/dev/**`（演示推进、角色切换）物理隔离，dev 包不打包进 prod 构建。
3. **CI 卡点**：至少加三条——`mvn test` 必须过、敏感字符串扫描（`123456`、`useSSL=false`、`cleartext`）命中即失败、`npm run build` 必须过。

### 8.3 关于 user-web 的处理建议

`user-web` 的 README 写得很好，明确声明"这是静态设计演示稿，交付以 frontend 为准"。这个自我定位是准确的，**建议保留但改名**，例如 `design-preview/`，避免新人误当产品代码维护。同时把它从构建流水线中排除。

### 8.4 三端 API 层不一致（对比结论）

| 维度 | frontend | admin-web |
|---|---|---|
| 实例 | 独立 axios，动态 baseURL（支持 App 手填服务器） | 独立 axios，固定 `/api/v1` |
| 身份头 | `X-User-Id` + `X-Rider-Id`（硬编码） | `X-Admin-Token`（localStorage） |
| 401 处理 | 无（仅 toast） | 有（logout + 跳登录） |
| 超时处理 | 统一 15s，无区分 | 区分 `ECONNABORTED` |
| 错误提示 | toast 组件 | 由视图自行处理 |

`admin-web` 的 API 层明显更成熟。建议**以 admin-web 为模板**统一三端：抽出共享 `request.js`（401 拦截、超时文案、错误归一），身份头改为统一 `Authorization`。这也是阶段二引入 JWT 时的自然落点。
